What is OneTool?

OneTool is a single static Linux ELF binary that bundles dozens of system tools into one executable. Instead of maintaining separate binaries for every utility (like the classic Unix toolbox), OneTool compiles everything into onetool — a single CLI entry point.

The core design principle: one executable, one CLI entry point, many capabilities implemented from scratch inside the project.

Architecture

Tool Registry

The tool_registry.h header defines the plugin-style API used by every tool:

typedef int (*onetool_entry_fn)(int argc, char *argv[]);

enum onetool_argv0_mode {
    ONETOOL_ARGV0_TOOL_NAME = 0,   // argv[0] = tool name
    ONETOOL_ARGV0_BINARY_PATH = 1, // argv[0] = binary path
};

struct onetool_tool {
    const char *name;          // Tool name (e.g. "ping")
    onetool_entry_fn entry;      // Entry function
    const char *description;    // Human-readable description
    enum onetool_argv0_mode argv0_mode;
};

Dispatcher Flow

  1. main() receives argc/argv
  2. If the first argument is "tui", it launches the TUI
  3. Otherwise it parses global flags like -to fd/path for output redirection
  4. It calls onetool_find_tool(name) which does a linear search over built-in and extra tools
  5. Found tool executes via onetool_run_tool() which sets argv[0] based on argv0_mode and calls the entry point
  6. Unknown tool names print help and return error

Extensibility

Tools can be added at build time without editing main.c by adding a line to config/extra_tools.manifest:

name|source|description|argv0_mode|extra_cflags
yap|mofl/languages/yap/yap.c|YAP language interpreter|tool|

The build system renames main() to a unique symbol automatically, compiles the source, and registers it into the tool table.

Build System

Requirements: clang, make. A custom build tool called lmake (implemented in Zig) is also bundled. Building produces the onetool static binary.

Build Steps

  1. Compile shared libraries: libs/TUI/ (ncurses wrapper), libs/elf/ (ELF64 parser), libs/memory/ (checked allocators), libs/net/ (HTTP, URL, TCP/TLS transport)
  2. Compile all built-in tools from tools/ — each tool's main() becomes a named entry point
  3. Run tools/dev/build_extra_tools.sh — reads config/extra_tools.manifest, compiles each extra tool with -Dmain= flag, automatically registering them
  4. Link everything into a single static ELF64 x86-64 executable

The result is a monolithic binary with no external runtime dependencies beyond Linux syscalls and libc.

1.5 API Functions — Complete Reference

int tui_init(void)

Initializes the ncurses terminal. Implementation steps:

  • Calls newterm(NULL, stdout, stdin) to initialize terminal
  • Enables cbreak() for character-by-character input
  • Disables echo() so typed keys don't show
  • Enables keypad(stdscr, TRUE) for arrow/function keys
  • Hides cursor via curs_set(0)
  • Sets escape delay to 25ms via set_escdelay(25) (if ncurses)
  • If colors are supported: calls start_color(), use_default_colors(), and apply_palette()
  • Returns 0 on success, 1 on failure

void tui_shutdown(void)

Restores terminal to its original state via endwin(). Safe to call multiple times — uses a static tui_ready flag.

void tui_begin_frame(void)

Calls clear() to erase the screen at the start of each frame.

void tui_end_frame(void)

Calls refresh() to flush all pending drawing operations to the terminal.

void tui_clear(int style)

Fills the entire screen with the background character space (' ') using the given style's color pair. Sets the background character via bkgdset() then clears.

void tui_get_size(int *width, int *height)

Uses getmaxyx(stdscr, max_y, max_x) to retrieve terminal dimensions. Sets width and height to 0 if TUI is not initialized.

int tui_poll_event(tui_event_t *event, int timeout_ms)

Polls for keyboard input:

  • Sets timeout(timeout_ms) for non-blocking input
  • Reads a key with getch()
  • If ERR (timeout), returns 0
  • Otherwise translates the raw keycode via translate_key(), sets event->kind and event->key, returns 1

Key translation: The translate_key() function maps ncurses KEY_* constants to OneTool's TUI_KEY_* enum. It handles: KEY_UP, KEY_DOWN, KEY_LEFT, KEY_RIGHT, KEY_HOME, KEY_END, KEY_PPAGE, KEY_NPAGE, KEY_DC (delete), KEY_BACKSPACE (and 127 and 8), \n \r KEY_ENTER, \t, ESC (27), KEY_RESIZE.

void tui_set_palette(const tui_palette_t *palette)

Copies the palette struct into the internal static tui_palette, then calls apply_palette() if colors are available and TUI is initialized. All color pairs are re-initialized with the new colors.

void tui_draw_text(int x, int y, int style, const char *text)

Draws text at screen position (x, y) using the given style:

  • Bounds-checks y against terminal height
  • Handles negative x by advancing the text pointer and reducing x to 0
  • Clips width to max_x - x
  • Uses mvaddnstr(y, x, text, width) with the style's attribute

void tui_draw_textf(int x, int y, int style, const char *fmt, ...)

Formats text with vsnprintf() (1024-byte buffer) then calls tui_draw_text().

void tui_fill_rect(int x, int y, int width, int height, int style, char fill)

Fills a rectangular area with a repeating character:

  • Clips rectangle to screen bounds via clip_rect_to_screen()
  • Uses nested loops with mvaddch() for each cell

void tui_draw_box(int x, int y, int width, int height, int style, const char *title)

Draws a bordered box:

  • Corners: ACS_ULCORNER, ACS_URCORNER, ACS_LLCORNER, ACS_LRCORNER
  • Edges: ACS_HLINE (horizontal), ACS_VLINE (vertical)
  • Title: If provided and box is wide enough, draws ACS_RTEE + title + ACS_LTEE on the top border, 2 characters from left

void tui_draw_hline(int x, int y, int width, int style, char ch)

Draws a horizontal line of repeated characters using mvaddch() in a loop.

void tui_draw_vline(int x, int y, int height, int style, char ch)

Draws a vertical line of repeated characters using mvaddch() in a vertical loop.

void tui_draw_status_line(int style, const char *text)

Draws a status bar at the bottom row of the terminal:

  • Fills the entire last row with spaces in the given style
  • Draws the text clipped to terminal width minus 1 using tui_clip_text()

int tui_key_is_printable(int key)

Returns 1 if key is in range 32-126 (printable ASCII), 0 otherwise.

const char *tui_clip_text(const char *src, char *dst, int dst_size, int width)

2. ELF Library — libs/elf/

Files: elf.h (52 lines), elf.c (172 lines)

A lightweight ELF64 parser that reads from memory buffers. Used by size, nm, and mlink tools. Supports little-endian ELF64 only.

2.1 Core Structures

ot_elf_section_t

Represents a single ELF section header entry after parsing:

typedef struct {
    char *name;            // Section name string (allocated, from .shstrtab)
    uint32_t name_offset;  // Raw index into .shstrtab
    uint32_t type;         // Section type: SHT_PROGBITS(1), SHT_NOBITS(8),
                          //   SHT_SYMTAB(2), SHT_STRTAB(3), SHT_RELA(4),
                          //   SHT_HASH(5), SHT_DYNAMIC(6), etc.
    uint64_t flags;        // SHF_WRITE(0x1), SHF_ALLOC(0x2), SHF_EXECINSTR(0x4),
                          //   SHF_MERGE(0x10), SHF_STRINGS(0x20), SHF_TLS(0x400)
    uint64_t addr;         // Virtual address at runtime (after loading)
    uint64_t offset;       // File offset
    uint64_t size;         // Section size in bytes
    uint32_t link;         // Link to another section (e.g. symtab→strtab index)
    uint32_t info;         // Extra info (e.g. symtab's last local symbol + 1)
    uint64_t addralign;    // Alignment requirement (power of 2)
    uint64_t entsize;      // Entry size for tables (e.g. 24 for symtab, 24 for rela)
} ot_elf_section_t;

ot_elf_file_t

Represents a fully parsed ELF file:

typedef struct {
    const char *name;           // File name (borrowed pointer, not owned)
    const unsigned char *data;  // Raw file data pointer
    size_t size;                // File size
    uint16_t type;              // ET_NONE(0), ET_REL(1), ET_EXEC(2), ET_DYN(3)
    uint16_t machine;           // EM_X86_64(62), EM_386(3), etc.
    uint64_t entry;             // Entry point virtual address
    uint16_t shstrndx;          // Section header string table index
    ot_elf_section_t *sections; // Parsed section array (allocated)
    size_t section_count;       // Number of sections
} ot_elf_file_t;

2.2 API Functions — Complete Reference

void ot_elf_init(ot_elf_file_t *elf)

Zero-initializes an elf file struct via memset(elf, 0, sizeof(*elf)). Must be called before ot_elf_parse().

void ot_elf_free(ot_elf_file_t *elf)

Frees all allocated resources:

  • Iterates through all sections and calls free() on each section's name
  • Frees the sections array
  • Zeroes the entire struct

int ot_elf_parse(ot_elf_file_t *elf, const char *name, const unsigned char *data, size_t size, char *err, size_t err_size)

Parses an ELF file from memory. Returns 0 on success, 1 on error.

Validation steps:

  1. Checks that data is at least EI_NIDENT (16) bytes and starts with ELF magic (0x7f 'E' 'L' 'F')
  2. Checks data is at least 64 bytes (minimum ELF64 header size)
  3. Checks EI_CLASS == ELFCLASS64 (2) — 32-bit ELF rejected
  4. Checks EI_DATA == ELFDATA2LSB (1) — big-endian rejected
  5. Checks EI_VERSION == EV_CURRENT (1)

Parsing steps:

  1. Reads section header table offset from offset 40 (8 bytes)
  2. Reads section header entry size from offset 58 (2 bytes) — must be 64
  3. Reads section count from offset 60 (2 bytes)
  4. Reads shstrndx from offset 62 (2 bytes)
  5. Validates section table fits in file via ot_elf_range_ok()
  6. Validates shstrndx is not SHN_UNDEF (0) and is within section count
  7. Allocates and parses all section headers (each 64 bytes)
  8. Reads the section string table, then resolves each section's name
  9. Sets metadata: type, machine, entry point, shstrndx

int ot_elf_range_ok(size_t file_size, uint64_t off, uint64_t size)

Validates that off + size fits within file_size:

return off <= file_size && size <= file_size - off;

This is the standard overflow-safe range check used throughout the ELF parser.

char *ot_elf_strdup_from_strtab(const unsigned char *base, size_t size, uint32_t off)

Extracts a null-terminated string from a string table at a given offset:

  • If offset is out of bounds, returns ""
  • Scans from offset until null byte or end of table
  • Allocates and copies the string via ot_xmalloc() + memcpy
  • If no null byte found before end, returns ""

3.1 URL Parser — url.c

net_url_t

typedef struct {
    char *host;    // Hostname (e.g. "example.com")
    char *port;    // Port string (e.g. "80" or "443")
    char *path;    // Path + query string (e.g. "/index.html?q=1")

int net_parse_http_url(const char *url, net_url_t *out)

Parses an HTTP/HTTPS URL. Returns 0 on success, 1 on error.

Parsing algorithm:

  1. Checks for "http://" prefix (7 chars) → no TLS
  2. Checks for "https://" prefix (8 chars) → TLS
  3. If no scheme prefix, defaults to HTTP
  4. Scans forward from host start to find '/' (path separator) or end of string
  5. Within host part, scans for ':' to detect explicit port
  6. If port found: splits host and port segments, allocates both
  7. If no port: allocates host, sets default port (443 for TLS, 80 otherwise)
  8. Sets path: defaults to "/" if empty, copies path_start otherwise
  9. All strings allocated with malloc()

void net_free_url(net_url_t *url)

Frees all allocated string fields (host, port, path) and zeroes the struct.

3.3 HTTP Layer — http.c

net_http_response_t

    int status_code;            // HTTP status code (200, 404, 500...)
    int chunked;                // 1 if Transfer-Encoding: chunked
    long long content_length;   // Content-Length header value (-1 if absent)

} net_http_response_t;

Internal Stream Type

typedef struct {
    net_conn_t *conn;           // Network connection
    const unsigned char *prefill;   // Already-read data buffer
    size_t prefill_len;             // Amount of prefill data available
    size_t prefill_pos;             // Current read position in prefill
} stream_t;

The stream_t type implements a buffered read layer over the connection. Initial HTTP response data that was read while searching for the header terminator is stored in prefill so it can be consumed before reading more data from the socket.

int net_http_send_request(net_conn_t *conn, const char *method, const char *path, const char *host, const char *headers[], int header_count, const char *body, const char *user_agent)

Builds and sends an HTTP/1.1 request. Returns 0 on success, 1 on failure.

Request construction:

METHOD path HTTP/1.1\r\n
Host: host\r\n
User-Agent: user_agent\r\n
Accept: */*\r\n
Connection: close\r\n
[custom headers...]\r\n
Content-Length: body_len\r\n
\r\n
body

The request is formatted into a 16KB static buffer using snprintf(). Custom headers are appended verbatim. Content-Length is included only if a body is provided. The request is sent via send_all() which handles partial writes and EINTR.

int net_http_read_response(net_conn_t *conn, FILE *out, int verbose, net_http_response_t *resp)

Reads and parses an HTTP response body. Returns 0 on success, 1 on failure.

Implementation details:

  1. Header accumulation: Reads data from socket in 8KB chunks into a dynamically growing buffer (initial 16KB, doubles as needed). Searches for "\r\n\r\n" (end of headers).
  2. Header parsing: Duplicates the header portion, tokenizes by "\r\n" with strtok(). Extracts status code from the first line. Scans for Content-Length and Transfer-Encoding: chunked headers.
  3. Body reading — chunked: Calls read_chunked() which loops: reads a hex chunk size line, reads that many bytes, writes them to output, reads trailing CRLF. Continues until a zero-length chunk, then consumes trailing headers.
  4. Body reading — content-length: First writes any prefilled data, then reads exactly content_length - prefilled more bytes in a loop.
  5. Body reading — connection close: (no content-length, no chunked) Reads until connection returns 0 bytes.
  6. Always flushes output via fflush(out).

Helper: static int send_all(net_conn_t *conn, const void *buf, size_t len)

Writes all len bytes to the connection, handling partial writes and EINTR. Returns 0 on success.

Helper: static int stream_read_exact(stream_t *s, unsigned char *dst, size_t len)

Reads exactly len bytes from the stream. Uses prefill buffer first, then reads from connection. Returns 0 on success.

Helper: static int stream_read_line(stream_t *s, char *line, size_t cap)

Reads one byte at a time until '\n' is found, then null-terminates. Returns 0 on success.

3.4 Robots.txt Checker — robots.c

int net_robots_is_allowed(const char *host, const char *port, int use_tls, int timeout_sec, const char *path, const char *user_agent, int verbose, int *allowed)

Fetches and parses /robots.txt from the target server, then checks if the given path is allowed for the given user agent.

Algorithm:

  1. Opens an HTTP connection to the server
  2. Sends a GET request for /robots.txt
  3. Reads the response body (non-chunked, connection-close mode)
  4. Parses line by line: User-agent:, Disallow:, Allow: directives
  5. Finds the matching user-agent section (first exact match, then wildcard *)
  6. Checks if the requested path matches any Disallow rule (prefix match)
  7. Sets *allowed to 0 (disallowed) or 1 (allowed)
  8. Returns 0 on success (fetch and parse worked), non-zero on fetch failure

4. Memory Library — libs/memory/

Files: memory.h (13 lines), memory.c (67 lines)

Checked allocation wrappers that abort on failure. Every heap allocation in OneTool goes through these to guarantee OOM safety without cluttering code with NULL checks.

4.1 Core Concepts

  • Non-zero size: All functions convert size 0 to 1 (nonzero_size()) to avoid implementation-defined malloc(0) behavior
  • Overflow protection: checked_mul() prevents integer overflow in multiplication (used by calloc and reallocarray)
  • Failure behavior: Prints "onetool: out of memory" to stderr and calls exit(2)

4.2 API Functions

void *ot_xmalloc(size_t size)

Wraps malloc(). If size is 0, allocates 1 byte. Aborts if NULL returned and size was non-zero.

void *ot_xcalloc(size_t count, size_t size)

Wraps calloc(). First computes total = count * size with overflow check (checked_mul()). Then allocates with calloc(1, total), converting 0 to 1. Aborts if NULL.

void *ot_xrealloc(void *ptr, size_t size)

Wraps realloc(). Converts size 0 to 1. Aborts if NULL returned.

void *ot_xreallocarray(void *ptr, size_t count, size_t size)

Computes total = count * size with overflow check, then calls ot_xrealloc(ptr, total).

char *ot_xstrdup(const char *s)

Wraps strdup(): computes length via strlen(), allocates len + 1 via ot_xmalloc(), copies with memcpy().

char *ot_xstrndup(const char *s, size_t len)

Wraps strndup(): allocates len + 1 via ot_xmalloc(), copies len bytes, null-terminates.

4.3 Private Helpers

static void oom(void) {
    fprintf(stderr, "onetool: out of memory\n");
    exit(2);
}

static size_t nonzero_size(size_t size) {
    return size == 0 ? 1 : size;
}

static size_t checked_mul(size_t count, size_t size) {
    if (count != 0 && size > SIZE_MAX / count) {
        oom();  // Overflow detected
    }
    return count * size;
}

1. Architecture Overview

1.1 Design Principles

  • Explicit control — no hidden state or implicit synchronization. Every operation is explicitly issued by the caller.
  • Backend agnosticism — the same API works across CPU, GPU DRM dumb buffers, i915 GEM, fbdev, and DRM display. Backend selection is a creation-time parameter.
  • Manual resource management — all objects are created/destroyed explicitly. No garbage collection or reference-counted sharing (except map/unmap refcounts).
  • Command buffer pattern — rendering commands are recorded into buffers and submitted as a batch for execution.
  • Minimal overhead — thin wrappers around native OS primitives (DRM ioctls, mmap, memcpy).

5. Device Management

A device represents a GPU or CPU resource provider. It owns a file descriptor (for DRM) and tile-cache state.

5.1 Device Probing

srapi_result_t srapi_probe_device(srapi_backend_t backend, srapi_device_info_t *out);
  • CPU/AUTO: always reports available (path="cpu")
  • GPU: delegates to srapi_gpu_probe() which scans /dev/dri/card0..card7 and renderD128..renderD135. A node is reported available only if a DRM dumb buffer can be created and mapped. The first usable node's path is returned.
  • FBDEV: checks /dev/fb0 for 32bpp support via FBIOGET_VSCREENINFO
srapi_result_t srapi_probe_i915(const char *device_path, srapi_i915_info_t *out);

Probes a specific path (or auto-scans render/card nodes) for i915 capabilities:

  • Verifies the DRM driver name via DRM_IOCTL_VERSION
  • Queries DRM_IOCTL_I915_GETPARAM for: chipset ID, GEM support, execbuf2, BLT engine, exec fence, CS timestamp frequency
  • A node is considered usable when GEM, execbuf2, and BLT are all present

6. Buffer System

6.1 Buffer Creation

srapi_result_t srapi_create_buffer(

7. Image System

Images are 2D allocations with width, height, pitch, and tiling mode.

12. Shader and Virtual Machine

The SRAPI shader system uses a custom bytecode VM with 16 general-purpose registers (32-bit float). Shaders can be used as fragment shaders (per-pixel) or vertex shaders (per-vertex).

12.1 Shader Creation

srapi_result_t srapi_create_shader(
    const uint32_t *bytecode,
    size_t word_count,
    const float *uniforms,     // may be NULL
    size_t uniform_count,      // may be 0
    srapi_shader_t **out
);
  • Copies bytecode, decodes instructions via vm_decode_bytecode()
  • Each bytecode word is uint32_t. Instruction format is variable-length:
ArgsOpcodes
0 argsEND
2 args (dst, a)MOV, LOAD_INPUT, LOAD_UNIFORM, FRACT, CLAMP01, SIN, COS, ABS, SQRT
1 arg + immediateLOAD_CONST (dst, imm32)
3 args (dst, a, b)ADD, SUB, MUL, DIV, MIN, MAX, POW
4 args (dst, a, b, c)MIX
4 args (a, b, c, d)OUT_COLOR (RGBA registers)
2 args (a, b)OUT_POSITION (x, y registers)

12.2 Uniform Management

srapi_result_t srapi_shader_set_uniform(srapi_shader_t *shader, size_t index, float value);
srapi_result_t srapi_shader_set_uniforms(srapi_shader_t *shader, size_t first,
                                          const float *values, size_t count);

12.3 Fragment Shader Execution

srapi_result_t srapi_vm_run_fragment(
    srapi_shader_t *shader,
    const float inputs[6],       // X, Y, U, V, WIDTH, HEIGHT
    srapi_color_t *out_color
);
  • 16 registers initialized to 0.0
  • Default output: magenta (255, 0, 255, 255) if OUT_COLOR is never executed
  • Shaders with OUT_POSITION ignore the position output in fragment mode
  • Debug trace for the first 2 runs (when global srapi flag is set)

12.4 Vertex Shader Execution

srapi_result_t srapi_vm_run_vertex(
    srapi_shader_t *shader,
    const float inputs[7],       // VERTEX_X, Y, R, G, B, A, INDEX
    float out_position[2],
    srapi_color_t *out_color
);
  • Same opcodes as fragment shader
  • OUT_POSITION writes to out_position[0] (x) and out_position[1] (y)
  • OUT_COLOR writes to out_color
  • Initial position and color are loaded from inputs[VERTEX_X/Y] and inputs[VERTEX_R/G/B/A]

13. CPU Software Renderer

The CPU rasterizer (backend/cpu/renderer.c) renders all command types into a framebuffer using software. It maintains a global render state (applied per-pixel).

13.1 Render State

void srapi_render_set_state(const srapi_render_state_t *state);
srapi_render_state_t srapi_render_default_state(const srapi_framebuffer_t *fb);
  • Scissor: if enabled, only pixels within the scissor rect are written. Applied in put_pixel().
  • Viewport: if enabled, vertex coordinates in [-1, 1] range are mapped to the viewport rect
  • Blend: SRAPI_BLEND_NONE overwrites; SRAPI_BLEND_ALPHA uses source-over: dst = src * src.a + dst * (1 - src.a) per channel

13.2 Pixel Writing

static void put_pixel(srapi_framebuffer_t *fb, int32_t x, int32_t y, srapi_color_t color);

Applies scissor and blend before writing to fb->pixels[y * pitch + x].

13.3 Clear

void srapi_render_clear(srapi_framebuffer_t *fb, srapi_color_t color);

Fills all pixels using a row pointer loop (no per-pixel function call overhead).

13.4 Rectangle Fill

void srapi_render_fill_rect(srapi_framebuffer_t *fb, int32_t x, int32_t y,
                            uint32_t w, uint32_t h, srapi_color_t color);

Clips the rectangle to framebuffer bounds, then fills with a nested loop calling put_pixel().

13.5 Line Drawing

void srapi_render_draw_line(srapi_framebuffer_t *fb, int32_t x0, int32_t y0,
                            int32_t x1, int32_t y1, srapi_color_t color);

Bresenham's integer line algorithm. Parameterizes the line by major axis and steps along it.

13.6 Triangle Fill

void srapi_render_fill_triangle(srapi_framebuffer_t *fb, int32_t x0, int32_t y0,
                                int32_t x1, int32_t y1, int32_t x2, int32_t y2,
                                srapi_color_t color);

Uses edge functions for point-in-triangle test. Computes bounding box, clips to framebuffer, and iterates pixels with the barycentric edgef() test.

13.7 Vertex Drawing

void srapi_render_draw_vertices(srapi_framebuffer_t *fb,
    srapi_primitive_topology_t topology,
    const srapi_vertex_t *vertices, size_t vertex_count,
    const uint32_t *indices, size_t index_count);

void srapi_render_draw_vertices_transformed(srapi_framebuffer_t *fb,
    srapi_primitive_topology_t topology,
    const srapi_vertex_t *vertices, size_t vertex_count,
    const uint32_t *indices, size_t index_count,
    const float *positions);
  • draw_vertices: applies viewport transform from NDC [-1,1] to viewport rect, then dispatches
  • draw_vertices_transformed: uses pre-transformed positions directly
  • Points: single-pixel point per vertex
  • Lines: Bresenham with color interpolation (mix between two vertex colors)
  • Triangles: edge-function rasterization with barycentric color interpolation using draw_vertex_triangle()
  • Sub-pixel accurate edge functions: shifts by 0.5 for pixel-center sampling

13.8 Shaded Rectangle

void srapi_render_shade_rect(srapi_framebuffer_t *fb, int32_t x, int32_t y,
                             uint32_t w, uint32_t h, srapi_shader_t *shader);

Clips to framebuffer bounds, then calls srapi_vm_shade_rect() which dispatches to SIMD or scalar execution with optional threading.

14. DRM/KMS Display Integration

The DRM display backend provides double-buffered scanout on a connected DRM/KMS output. It lives in backend/drm/ (display logic) and display/drm_probe.c (enumeration).

14.1 Display Detection

srapi_result_t srapi_display_probe_drm(
    const char *device_path,       // NULL = auto-scan
    srapi_display_info_t *out,    // array of results
    size_t out_count,
    size_t *written
);

srapi_result_t srapi_display_list_modes_drm(
    const char *device_path,
    uint32_t connector_id,
    srapi_display_mode_t *out,    // array of modes
    size_t out_count,
    size_t *written
);

Probe scans DRM resources (connectors, CRTCs, planes) and returns connected outputs with their preferred modes. Modes list returns all available display modes for a specific connector.

14.2 Display Open

srapi_result_t srapi_drm_open(const char *device_path, srapi_drm_display_t **out);
srapi_result_t srapi_drm_open_display(
    const srapi_drm_display_desc_t *desc,
    srapi_drm_display_t **out
);
  1. Opens the DRM device (auto-detects card0..card7 if path is NULL)
  2. Loads DRM resources, finds a connected connector
  3. Chooses a compatible CRTC
  4. Selects display mode (preferred by default, or from desc)
  5. Creates two dumb buffers for double buffering via srapi_drm_create_buffer():
    • Creates dumb buffer with DRM_IOCTL_MODE_CREATE_DUMB
    • Adds framebuffer with drmModeAddFB
    • Maps with DRM_IOCTL_MODE_MAP_DUMB + mmap
  6. Sets CRTC mode with drmModeSetCrtc
  7. Saves old CRTC state for restore on close

14.3 Frame Access

srapi_framebuffer_t *srapi_drm_framebuffer(srapi_drm_display_t *display);  // current front
srapi_framebuffer_t *srapi_drm_backbuffer(srapi_drm_display_t *display);   // current back

The front buffer is the one being scanned out. Render to the backbuffer, then present.

14.4 Presentation

srapi_result_t srapi_drm_present(srapi_drm_display_t *display);
  1. Tries drmModePageFlip for a vsynced flip
  2. If flip fails (e.g., missing DRM_CLIENT_CAP_ATOMIC), falls back to drmModeSetCrtc
  3. Waits for page flip completion event via poll() on the DRM fd
  4. Swaps front/back buffer indices

14.5 Mode Management

15. GPU Backend

The GPU backend (backend/gpu/gpu.c) provides generic DRM dumb-buffer resource allocation. It is used for both non-i915 GPUs and as a fallback for i915.

15.1 Probing

srapi_result_t srapi_gpu_probe(srapi_device_info_t *out);

Scans /dev/dri/card0..card7 and renderD128..renderD135. For each node:

  1. Opens the node
  2. Attempts DRM_IOCTL_MODE_CREATE_DUMB (64 bytes)
  3. Attempts DRM_IOCTL_MODE_MAP_DUMB
  4. Mmaps the buffer
  5. If all succeed, the node is reported as available

This avoids selecting render-only nodes that open but cannot back SRAPI GPU resources.

18. Tile Cache System

The tile cache (core/tile_cache.c) provides content-aware incremental rendering. The framebuffer is divided into a grid of tiles. For each tile, a hash of the command buffer state is computed. If the hash matches the previous frame, the tile is skipped (not re-rendered).

18.1 Configuration

Configured via the device:

srapi_device_set_tile_cache_enabled(device, 1);
srapi_device_set_tile_cache_config(device, cols, rows);  // tile grid

18.2 Hash Computation

Three hash functions:

  • tc_shader_hash() — hashes shader bytecode + uniforms
  • tc_command_hash() — hashes command parameters (kind, color, position, shader pointer, topology, vertex/index buffer pointers)
  • tc_tile_hash() — combines command hash, shader hash, and tile position into a final 64-bit hash

18.3 Submission

srapi_result_t srapi_tile_cache_submit_framebuffer(
    srapi_device_t *device,
    srapi_framebuffer_t *target,
    const srapi_cmd_buffer_t *cmd
);
  1. Computes hash for each tile based on the command buffer content
  2. If hash matches device->tile_hashes[tile_index], skips the tile
  3. For changed tiles, dispatches rendering:
    • If i915 BLT is available: srapi_i915_render_tile_region()
    • Otherwise: CPU rasterizer via cpu_render_tile() (clones command buffer for the tile region and calls srapi_submit)
  4. Updates tile_hashes[tile_index] with the new hash

19. SIMD Shader Execution

The SIMD shader execution engine (vm/exec_simd.c) accelerates fragment shaders using AVX (Advanced Vector Extensions), processing 8 pixels simultaneously.

19.1 Overview

  • Uses __m256 (8-wide single-precision SIMD) registers
  • Implements all 21 VM opcodes with SIMD equivalents where possible
  • Fallback to scalar for SIN, COS, POW (using scalar_unary8 / scalar_binary8)
  • Safe division: replaces zero divisors with 1.0 before division, zeros the result where divisor was zero

19.2 Entry Point

srapi_result_t srapi_vm_shade_rect(
    uint32_t *pixels,
    uint32_t pitch_bytes,
    srapi_shader_t *shader,
    int32_t rect_x0, int32_t rect_y0,
    uint32_t rect_width, uint32_t rect_height,
    uint32_t x, uint32_t y,        // clip region
    uint32_t width, uint32_t height
);

Decision flow:

  1. If shade_config.simd_enabled == 0: calls scalar fallback (shade_scalar)
  2. If shade_config.threads_enabled == 0: calls SIMD directly (shade_tile_rows)
  3. Otherwise: splits the region into 32-row tiles and dispatches via thread pool

19.3 SIMD Pixel Pipeline

  1. shade_tile_rows() iterates rows; for each row, processes 8-pixel chunks
  2. run_chunk() executes all instructions on 8-wide vectors:
    • Registers: 16 __m256 values, all zero-initialized
    • Inputs: X, Y, U, V, WIDTH, HEIGHT as SIMD vectors
    • Uniforms: broadcast to all lanes
    • Constants: broadcast from uint32_t bit pattern
  3. emit_pixels() converts RGBA floats to packed ARGB uint32_t, clamps to [0,1], multiplies by 255, rounds with +0.5, and stores via _mm256_storeu_si256 (full 8 pixels) or _mm256_maskstore_epi32 (partial last chunk)

20. Thread Pool

The thread pool (vm/threadpool.c) enables parallel tile rendering for shaded rectangles.

20.1 Design

  • Up to 63 worker threads (SRAPI_VM_MAX_WORKERS)
  • Threads are created once via pthread_once
  • Workers sleep on a pthread_cond_t waiting for work
  • Work is dispatched as tiles; workers atomically fetch and increment a tile counter

20.2 API

typedef void (*srapi_vm_tile_fn_t)(void *user, uint32_t tile_index);

void srapi_vm_threadpool_dispatch(
    uint32_t tile_count,
    srapi_vm_tile_fn_t fn,
    void *user
);

The calling thread participates by processing tiles after waking workers. The function returns when all tiles are complete.

23. Image Output (PPM/BMP)

23.1 PPM Format

  • P6 (binary) format
  • Header: P6\n<width> <height>\n255\n
  • Pixel data: RGB bytes, top-left to bottom-right, alpha discarded

23.2 BMP Format

  • 24-bit BITMAPINFOHEADER (54-byte header)
  • Pixel data: BGR bytes (blue-green-red), bottom-up row order
  • Each row is zero-padded to 4-byte alignment
  • Alpha channel discarded

24. Current Limitations

  • 2D rendering only; no 3D graphics pipeline
  • No depth/stencil buffer support
  • No Wayland/X11 display integration (direct DRM/KMS or fbdev only)
  • fbdev: 32bpp only, no mode setting, no double buffering
  • i915 BLT path: only CLEAR, FILL_RECT, SET_SCISSOR, and SET_VIEWPORT (no-op) are accelerated; lines, triangles, vertex draws, shaders, and alpha blending fall back to CPU
  • Single-threaded for CPU rasterizer (threading only applies to shader-based shading)
  • No async command submission or timeline semaphores
  • Shader VM is interpreted (no JIT compilation)
  • i915 render3d/vm modules write CPU-side into mapped GEM memory (not GPU-executed shaders)
  • No Vulkan or OpenGL backend
  • Tile cache hashes are linear and do not support GPU-computed hashing

nm — ELF Symbols

Source: tools/filesystem/nm.c

Entry: nm()

Prints symbols from an ELF symbol table. Mimics classic Unix nm(1) in spirit.

Implementation

  1. Parses the ELF file using ot_elf_parse() from libs/elf
  2. Locates the SHT_SYMTAB section (symbol table)
  3. Reads each symbol entry (24 bytes each for ELF64): name (via strtab offset), value (8 bytes), size (8 bytes), info (1 byte: bind+type), other (1 byte), shndx (2 bytes)

  • D / d — Data section symbol
  • B / b — BSS symbol

  • ? — Unknown/unclassified

CLI Parsing — parse_opts()

Parses options from argv[] into ping_opts_t. Uses value helpers with range validation:

  • parse_int() — uses strtol(), validates range [min_v, max_v], rejects trailing garbage
  • parse_double() — uses strtod(), validates range [min_v, max_v]
  • Flags: -c (count, 1-1000000), -W (timeout ms, 1-600000), -s (payload size, 0-1400), -i (interval, 0.01-3600.0), -q/--quiet, -h/--help
  • Defaults: count=4, timeout=1000ms, payload=56, interval=1.0, quiet=0

ICMP Packet Construction

  1. Packet buffer: 1500-byte buffer (max Ethernet MTU). Total packet size = sizeof(icmphdr) + sizeof(timeval) + payload_size
  2. ICMP header fields:
    • icmp->type = ICMP_ECHO (8) — echo request
    • icmp->code = 0
    • icmp->un.echo.id = htons(pid & 0xFFFF) — process ID to match replies
    • icmp->un.echo.sequence = htons(seq) — sequence number 1..count
  3. Timestamp embedding: Immediately after the ICMP header, gettimeofday(&send_tv) is stored — this is used later to compute RTT by comparing with the reception timestamp
  4. Payload fill: Remaining bytes are filled with a predictable pattern (i & 0xFF)
  5. Checksum: Computed via the standard Internet checksum algorithm on the entire packet (header + timestamp + payload) using icmp_checksum()

Send and Receive Loop

For each sequence number from 1 to count:

  1. Build packet as described above
  2. Send: sendto(sock, packet, pkt_len, 0, &dst, sizeof(dst)) — increments tx counter. On send error: prints ping: sendto failed: strerror and continues to next sequence
  3. Poll: poll(&pfd, 1, timeout_ms) — waits for data on the raw socket:
    • Timeout (0): Prints request timeout icmp_seq N
    • Error (<0): Handles EINTR (ignore), otherwise prints poll error
    • Data available (>0): Calls recvfrom() into a 2048-byte buffer
  4. Reply parsing: Validates the received packet is at least sizeof(iphdr) + sizeof(icmphdr) bytes. Parses the IP header to get IHL (IP header length, typically 20 bytes). Extracts the ICMP header from recvbuf + ihl:
    • Checks ri->type == ICMP_ECHOREPLY (0)
    • Checks ntohs(ri->un.echo.id) == pid_id — matches our process ID to avoid picking up other ping replies
    • Reads embedded timestamp from recvbuf + ihl + sizeof(icmphdr)
    • Computes RTT via ms_since(&sent_in_pkt, &recv_tv) — difference in microseconds converted to milliseconds
    • Updates min/max/sum RTT statistics, increments rx counter
    • If not quiet: prints N bytes from IP: icmp_seq=N ttl=N time=XXX.XXX ms
  5. Inter-packet delay: If not the last packet, calls usleep(interval_sec * 1000000)

Statistics Summary

After the loop:

  • Prints the target hostname/IP
  • If any packets were transmitted: prints N packets transmitted N received X.X% packet loss
  • If any replies were received: prints rtt min/avg/max = X.XXX/X.XXX/X.XXX ms
  • Returns 0 if at least one reply was received, 1 otherwise

ICMP Checksum — icmp_checksum()

static unsigned short icmp_checksum(const void *data, size_t len) {
    const unsigned short *p = data;
    unsigned int sum = 0;
    while (len > 1) {
        sum += *p++;
        len -= 2;
    }
    if (len == 1)
        sum += *(const unsigned char *)p;
    while (sum >> 16)
        sum = (sum & 0xFFFF) + (sum >> 16);
    return ~sum;
}

This is the standard 16-bit one's complement Internet checksum (RFC 1071). Used by ICMP, IP, TCP, and UDP. The algorithm sums 16-bit words, folds carries, and returns the bitwise complement.

RTT Calculation — ms_since()

static double ms_since(const struct timeval *start, const struct timeval *end) {
    double sec = (double)(end->tv_sec - start->tv_sec);
    double usec = (double)(end->tv_usec - start->tv_usec);
    return sec * 1000.0 + usec / 1000.0;
}

Computes the difference between two struct timeval timestamps in milliseconds as a double (microsecond precision). This handles the full range of possible RTT values without overflow.

Error Handling

  • Payload overflow: If computed packet size exceeds 1500 bytes, prints error and exits
  • Invalid options: All option values have min/max bounds checking with descriptive error messages

cvm — Current Video Mode

Source: tools/system/video/cvm.c (61 lines)

Entry: cv()

Displays the current video mode and screen resolution by querying the Linux framebuffer device (/dev/fb0) via ioctl() and /sys/class/graphics/fb0/modes.

Implementation

The tool is a single C function print_fb_info() plus main():

  1. Framebuffer detection: Attempts to open /dev/fb0 with open("/dev/fb0", O_RDONLY). If the device doesn't exist or can't be opened (e.g., no framebuffer driver, running in a VM without fbdev, or in text mode), prints "video mode: vga text mode (no framebuffer detected)" and returns.
  2. ioctl queries: Uses two Linux framebuffer ioctls on the opened fd:
    • FBIOGET_VSCREENINFO — fills struct fb_var_screeninfo with variable screen parameters:
      • xres, yres — current visible resolution (e.g. 1920×1080)
      • xres_virtual, yres_virtual — virtual buffer size (may be larger than visible for panning)
      • bits_per_pixel — color depth (e.g. 32 for ARGB8888)
    • FBIOGET_FSCREENINFO — fills struct fb_fix_screeninfo with fixed parameters:
      • id — driver name string (e.g. "efifb", "vesafb", "simpledrm", "bochs-drm")
  3. Sysfs max resolution: Opens /sys/class/graphics/fb0/modes and reads all lines. Each line is a mode descriptor in the format "WxHp-bpp@refresh" (e.g. "1920x1080p-32"). The tool iterates through all lines and stores the last one (which is typically the highest/available mode in the sysfs list). This provides information about what resolutions the framebuffer driver can support, beyond the current setting.
  4. Cleanup: Closes the framebuffer fd and returns.

Output Format

Notes

  • No framebuffer: On systems without /dev/fb0 (e.g., modern systems using KMS/drm only, or SSH sessions), the tool reports "vga text mode (no framebuffer detected)". This is not an error — it's expected behavior on headless systems or when the framebuffer driver isn't loaded.
  • Driver names: Common values for finfo.id include "efifb" (UEFI GOP framebuffer), "vesafb" (VESA BIOS framebuffer), "simpledrm" (simpledrm driver), and "bochs-drm" (QEMU/Bochs virtual GPU).
  • KMS note: This tool uses the legacy fbdev interface, not KMS (kernel modesetting). Modern Linux graphics are moving toward KMS/drm, but fbdev is still widely available via the simpledrm or compatibility layers.
  • Sysfs modes: The /sys/class/graphics/fb0/modes file may not exist on all systems — in that case, only the current resolution from ioctl is shown.

Archive Parsing — load_archive()

mlink supports three archive formats:

  • POSIX/BSD style (#1/ prefix): The member name is stored at the beginning of the member data, followed by the actual object content
  • GNU style (/123 long names): The archive has a // member containing a string table; member names reference offsets into it
  • Standard short names (16-byte header field): Names are stored directly in the archive header, space-padded, with optional trailing '/'

The parser also skips symbol table members (/ and /SYM64/). Archive member alignment is enforced (odd sizes are padded).

Linking Pipeline — 6 Phases

Phase 1: Load Inputs (ml_load_input())

Each input path is read from disk via ml_read_file(). The file is identified as either:

  • Archive (.a): Checked via ARMAG magic ("!\n"). Parsed by load_archive(), each ELF object within is parsed and added to the context as an unselected archive member.
  • ELF object (.o): Checked via ELFMAG magic. Parsed by ml_parse_elf_object() and added as a selected (non-archive) object.

Phase 2: Parse ELF Objects (ml_parse_elf_object())

Uses the shared ot_elf_parse() from libs/elf to validate the ELF header, then:

  1. Section loading: Copies section names, types, flags, sizes, aligns. Classifies each section via classify_section(). Copies section data for PROGBITS sections.
  2. Symbol loading: Locates SHT_SYMTAB (entry size must be 24). For each symbol: reads name, bind (STB_GLOBAL/STB_LOCAL/STB_WEAK), type, shndx, value, size, and determines if undefined or common.
  3. Relocation loading: Locates SHT_RELA (entry size 24) and SHT_REL (entry size 16). For each relocation: reads offset, symbol index, type, and addend (if RELA).

Phase 3: Symbol Resolution (ml_resolve_symbols())

Three sub-steps:

3a. Archive Member Selection (select_archive_members())

Iterates archive members in a fixed-point loop. For each unselected archive member, if any of its defined global symbols are referenced by already-selected objects, the member becomes selected. This loop repeats until no more members are selected (standard Unix linker semantics).

3b. Global Symbol Definition (define_global())

For each selected object's global symbols:

  • Common symbols: If not already defined, the largest size wins (standard COMDAT-like behavior)
  • Defined symbols: If already defined, strong overrides weak; duplicate strong symbols produce an error; duplicate weak symbols are ignored
3c. Undefined Reference Tracking (record_undefined())

Records all undefined references. After resolution, any symbol that is strongly referenced but neither defined nor common produces an "undefined symbol" error.

Phase 4: Layout (ml_layout())

Computes output addresses and file offsets for all sections:

4a. Segment Detection

Scans all sections to determine which segments are needed:

  • RX segment — required if any TEXT sections exist
  • RO segment — required if any RODATA sections exist
  • RW segment — required if any DATA, BSS, or COMMON symbols exist
4b. Section Ordering

Sections are assigned in this order within each object:

  1. .text sections — aligned, placed in RX segment
  2. .rodata sections — aligned, page-aligned boundary from RX end
  3. .data sections — aligned, page-aligned boundary from RO end
  4. .bss sections — placed after .data (not written to file)

Common symbols are placed after all data sections, with their requested alignment. The largest alignment wins. The BSS memory size is extended to cover common symbols.

Each global symbol's value is computed:

  • Defined symbols: section.out_addr + symbol.value
  • Absolute symbols: symbol.value (SHN_ABS)
  • Common symbols: base_addr + common_cursor (with alignment)

All selected objects' sections are copied to the output buffer at their assigned offsets. BSS sections are not copied (they are zero-initialized by the OS loader).

Parser — Parser struct

The parser consumes tokens and constructs a program model with two main data structures:

Program Model

const Program = struct {
    vars: std.StringArrayHashMap([]const u8),       // Variable name → value
    task_order: std.ArrayListUnmanaged([]const u8), // Task names in definition order
    tasks: std.StringArrayHashMap(Task),             // Task name → Task struct
};

const Task = struct {
    name: []const u8,         // Task name (e.g. "all", "clean")
    body: []const u8,         // Raw command text to execute
    deps: [][]const u8,       // Dependency task names
};

Parsing rules:

  • Variable declaration: string NAME = "value"; — stores in program.vars. Variables can reference other variables using @(NAME) syntax in string values.
  • Task definition: task "name" [deps...] { body } — stores the task name, dependency list, and body text.
  • Variable references: Inside string values, @(VARNAME) is replaced with the variable's value during variable loading (before execution). References are resolved with dependency order: the parser collects all @(...) references and substitutes them by looking up in program.vars.

Executor — Executor struct

The executor runs tasks by invoking system commands via shell:

loadVars()

Iterates all declared variables in definition order. For each variable, scans the value for @(NAME) references and substitutes them. This enables variables to reference previously defined variables (e.g., MAIN_OBJ = "main.o" and later OBJS = "@(MAIN_OBJ) tools.o").

execTask(name)

  1. Looks up the task by name in program.tasks
  2. If not found: tries "all" or the first task in definition order
  3. Recursively executes all dependency tasks first (via execTask())
  4. If the task has a body, substitutes variable references in the body text using @(NAME) syntax
  5. Executes the substituted command via std.Io.Command.run() which spawns a shell (/bin/sh -c "...")
  6. Checks the exit code — if non-zero, returns error.CommandFailed

format() — Custom Formatter

A printf-style string formatter supporting:

  • %s — string
  • %d, %i — signed integer
  • %u — unsigned integer
  • %x, %X — hexadecimal (lower/upper)
  • %b — binary
  • %c — character from integer value
  • %% — literal percent
  • Padding: %10s (right-align), %-10s (left-align), %010d (zero-padded)

All numeric formatting uses std.fmt.parseInt() for parsing and std.fmt.bufPrint() for output. Arguments are passed as []const u8 slices and parsed to integers on demand.

CLI Entry — runLmake()

Parses command-line arguments:

lmake [-f ] [target]
lmake --list          # list available targets
lmake -h, --help      # show usage
  • Default file: lmakefile in the current directory
  • Default target: "all" if defined, otherwise the first task in the file
  • --list: Prints all task names in definition order

Reads the lmakefile (max 10MB via .limited(10 * 1024 * 1024)), parses it, loads variables, finds the entry target, then executes it with full dependency resolution.

C ABI Export — lk()

The lk() function is exported with pub export fn so it can be called by OneTool's C dispatcher with standard C ABI (argc/argv):

  • Creates a std.Io instance with threaded I/O and inherits the process environment from std.c.environ
  • Uses a DebugAllocator for the main heap and an ArenaAllocator for the parser/executor (all memory freed at once via arena.deinit())
  • Converts C argv pointers to Zig slices
  • Calls runLmake() — on error, prints the error name and returns 1
  • Returns 0 on success

OneTool — Power Management Tools

The power management subsystem consists of two minimal tools for system reboot and shutdown. Both are implemented in a single C file each (~50 lines) and use the reboot() Linux syscall directly — no systemctl, shutdown, or external process spawning.

reboot — Reboot System

Source: tools/power/reboot.c (46 lines)

Entry: rb()

Reboots the system immediately or after a configurable delay. Uses the reboot() system call with LINUX_REBOOT_CMD_RESTART.

Implementation Details

  1. Argument parsing: Accepts an optional -t seconds flag. The value is parsed with strtol() — includes validation for: no characters consumed (end == argv[2]), trailing garbage (*end != '\0'), negative values, and values exceeding INT32_MAX (2,147,483,647 seconds ≈ 68 years).
  2. Delay: If a delay was specified, calls sleep(delay) before proceeding.
  3. sync(): Calls sync() to flush filesystem buffers before triggering the reboot — critical for data integrity.
  4. Syscall: Calls reboot(LINUX_REBOOT_CMD_RESTART) which sends the magic shutdown sequence 0xfee1dead + 672274793 to the kernel via the __NR_reboot syscall. On error, prints the errno string via strerror(errno) and returns 1.

Error handling: Prints invalid timer value: for bad formats, timer value is too large for overflow, and reboot failed: if the syscall fails (typically due to missing CAP_SYS_BOOT capability).

Usage

onetool reboot [-t seconds]
OptionDescription
-t secondsWait the specified number of seconds before rebooting

Examples

# Reboot immediately
onetool reboot

# Reboot after 5 seconds
onetool reboot -t 5

Note: Requires CAP_SYS_BOOT (typically root). The delay is a simple sleep() — it blocks the process before the reboot syscall.

shutdown — Power Off System

Source: tools/power/shutdown.c (46 lines)

Entry: sd()

Powers off the system immediately or after a configurable delay. Uses the reboot() system call with LINUX_REBOOT_CMD_POWER_OFF.

Implementation Details

Structurally identical to reboot.c except:

  • Syscall: Uses LINUX_REBOOT_CMD_POWER_OFF instead of LINUX_REBOOT_CMD_RESTART. This triggers kernel shutdown sequence that ACPI power-off on supported hardware.
  • Error message: Prints shutdown failed: instead of reboot failed.
  • Argument parsing: Same strtol-based parsing with full validation — identical to reboot.

Usage

onetool shutdown [-t seconds]
OptionDescription
-t secondsWait the specified number of seconds before shutting down

Examples

# Shut down immediately
onetool shutdown

# Shut down after 10 seconds
onetool shutdown -t 10

Note: Requires CAP_SYS_BOOT (typically root). On systems without ACPI or virtual machines without proper power-off support, the kernel may hang after printing "Power down."

Common Syscall Behaviour

Both tools use the same underlying reboot() libc wrapper, which invokes the __NR_reboot syscall (169 on x86-64). The kernel requires the caller to have CAP_SYS_BOOT in the user namespace. The magic arguments to the syscall are:

ParameterValue
magic10xfee1dead
magic2672274793 (LINUX_REBOOT_MAGIC2)
cmdLINUX_REBOOT_CMD_RESTART (reboot) or LINUX_REBOOT_CMD_POWER_OFF (shutdown)

OneTool — Configuration & Extensibility

This document covers how tools are registered, how new tools can be added, the build system, output redirection, and the init system integration.

Tool Registry System

The registry API defined in config/tool_registry.h provides the plugin-style interface that every OneTool tool must conform to.

1. Tool Entry Function

typedef int (*onetool_entry_fn)(int argc, char *argv[]);

Every tool must expose a function with this signature. It receives argc/argv just like a normal main(). Tools can be implemented as standard C programs with int main(int argc, char *argv[]) — the build system renames main to a unique symbol automatically.

2. argv0 Mode

enum onetool_argv0_mode {
    ONETOOL_ARGV0_TOOL_NAME = 0,   // argv[0] set to tool name (most tools)
    ONETOOL_ARGV0_BINARY_PATH = 1, // argv[0] set to binary path (lmake)
};

TOOL_NAME mode is standard for utilities — argv[0] becomes the tool name like "ping". BINARY_PATH mode is used by tools that inspect their own binary location (like lmake, which needs to find build scripts relative to the executable).

3. Tool Structure

struct onetool_tool {
    const char *name;          // CLI name (e.g., "ping")
    onetool_entry_fn entry;      // Entry function pointer
    const char *description;    // Help description
    enum onetool_argv0_mode argv0_mode;
};

The tool table is an array of these structs. The dispatcher iterates the array linearly to find a tool by name. Unrecognized tool names print the full tool list as help.

Adding Built-in Tools (no manifest)

Built-in tools are declared in main.c in the onetool_builtin_tools[] array. To add a new built-in tool:

  1. Implement a function with signature int my_tool(int argc, char *argv[]) (or keep it as main() if using the manifest system)
  2. Add a forward declaration at the top of main.c
  3. Add an entry to onetool_builtin_tools[] with name, function pointer, description, and argv0 mode
  4. Rebuild

Current built-in tools registered in main.c: lm (lastmod), ex (exec), fi (fsinfo), fz (fsize), sz (size), nm (nm), rb (reboot), sd (shutdown), ml (mlink), ga (gapi_supported), lp (lpack), pg (ping), ns (nsetup), dn (down), tm (taskmng), uc (userc), cf (configure), cv (cvm), lk (lmake).

Build Process for Extra Tools

The build script tools/dev/build_extra_tools.sh processes the manifest as follows:

  1. Reads the manifest line by line, splitting on | delimiter
  2. For each entry, generates a unique symbol name: onetool_extra_main_
  3. Compiles the source file with -Dmain=onetool_extra_main_ — this renames the tool's main() function to the generated symbol via the C preprocessor
  4. Passes any extra_cflags to the compiler
  5. The resulting object file is linked into the onetool binary
  6. At startup, the extra tools are registered via the auto-generated onetool_extra_tools[] array
  7. The onetool_find_tool() function searches built-in tools first, then extra tools

This mechanism allows third-party tools to be plugged in without touching any core source files.

Global Output Redirection

OneTool supports a global -to flag that redirects stdout and stderr of any tool invocation:

onetool ping 1.1.1.1 -to /tmp/ping.log
onetool down https://example.com -to fd   # redirect to fd 3

When -to is used, the dispatcher in main() intercepts it before calling the tool:

  • If the argument is "fd", no action is taken — the caller is expected to have already set up file descriptor 3 for output capture. This is used by the TUI when running tools with output capture.
  • Otherwise, the argument is treated as a file path. The file is opened with open(path, O_WRONLY|O_CREAT|O_TRUNC, 0644), and both stdout (fd 1) and stderr (fd 2) are duplicated to the file descriptor via dup2().

Note: The -to flag must appear after the tool name, not as a global flag before it. The tool's main() never sees the -to flag — it is consumed by the dispatcher before calling the entry point.

The bundled lmake (tools/dev/lmake.zig) is written in Zig and compiled separately. It is registered with ONETOOL_ARGV0_BINARY_PATH mode so it can locate build scripts relative to the binary path. The lmakefile in the project root is the build definition consumed by lmake — it replaces a traditional Makefile with OneTool's own build system.

InitFS

The initfs/init file is an embedded init script designed for minimal Linux environments where OneTool acts as /init (PID 1). This enables OneTool to function as the sole binary in a tiny root filesystem — a self-contained userspace.

Bootstrap Process

When OneTool is used as init:

  1. The kernel starts OneTool as PID 1
  2. If the TUI tool is launched (or taskmng/userc), the configure tool (cf) is called automatically as a fallback: if tui_init() (which needs /dev/tty) fails, it runs configure first, then retries TUI initialization
  3. Configure mounts /proc, /sys, /dev (devtmpfs), and /tmp (tmpfs) to bootstrap the basic Linux filesystem layout
  4. After this bootstrap, the full TUI becomes available

Makefile Details (lmakefile)

The project root contains lmakefile which is the build definition consumed by lmake. This is a custom build system format — not GNU Make syntax. It defines:

  • Source file lists for each tool
  • Library dependencies
  • CFLAGS, LDFLAGS
  • Output binary name and location

Error Handling Conventions

All OneTool tools follow consistent conventions:

  • Return value: 0 for success, 1 for failure
  • Errors: Printed to stderr with fprintf(stderr, ...) and strerror(errno) for system call failures
  • Usage: Invalid arguments print usage to stderr and return 1
  • Memory: All heap allocations go through ot_x*() wrappers that abort on OOM
