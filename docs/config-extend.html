OneTool — Configuration & Extensibility

This document covers how tools are registered, how new tools can be added, the build system, output redirection, and the init system integration.

Tool Registry System

The registry API defined in config/tool_registry.h provides the plugin-style interface that every OneTool tool must conform to.

1. Tool Entry Function

typedef int (*onetool_entry_fn)(int argc, char *argv[]);

Every tool must expose a function with this signature. It receives argc/argv just like a normal main(). Tools can be implemented as standard C programs with int main(int argc, char *argv[]) — the build system renames main to a unique symbol automatically.

2. argv0 Mode

enum onetool_argv0_mode {
    ONETOOL_ARGV0_TOOL_NAME = 0,   // argv[0] set to tool name (most tools)
    ONETOOL_ARGV0_BINARY_PATH = 1, // argv[0] set to binary path (lmake)
};

TOOL_NAME mode is standard for utilities — argv[0] becomes the tool name like "ping". BINARY_PATH mode is used by tools that inspect their own binary location (like lmake, which needs to find build scripts relative to the executable).

3. Tool Structure

struct onetool_tool {
    const char *name;          // CLI name (e.g., "ping")
    onetool_entry_fn entry;      // Entry function pointer
    const char *description;    // Help description
    enum onetool_argv0_mode argv0_mode;
};

The tool table is an array of these structs. The dispatcher iterates the array linearly to find a tool by name. Unrecognized tool names print the full tool list as help.

Adding Built-in Tools (no manifest)

Built-in tools are declared in main.c in the onetool_builtin_tools[] array. To add a new built-in tool:

  1. Implement a function with signature int my_tool(int argc, char *argv[]) (or keep it as main() if using the manifest system)
  2. Add a forward declaration at the top of main.c
  3. Add an entry to onetool_builtin_tools[] with name, function pointer, description, and argv0 mode
  4. Rebuild

Current built-in tools registered in main.c: lm (lastmod), ex (exec), fi (fsinfo), fz (fsize), sz (size), nm (nm), rb (reboot), sd (shutdown), ml (mlink), ga (gapi_supported), lp (lpack), pg (ping), ns (nsetup), dn (down), tm (taskmng), uc (userc), cf (configure), cv (cvm), lk (lmake).

Adding Extra Tools via Manifest

Tools can be added without modifying main.c by using the extra tools manifest at config/extra_tools.manifest.

Manifest Format

name|source|description|argv0_mode|extra_cflags

Fields:

FieldDescriptionExample
nameCLI tool nameyap
sourcePath to C source file (relative to project root)mofl/languages/yap/yap.c
descriptionHelp text for tool listYAP language interpreter
argv0_modetool or onetooltool
extra_cflagsAdditional compiler flags (optional)-lm

Build Process for Extra Tools

The build script tools/dev/build_extra_tools.sh processes the manifest as follows:

  1. Reads the manifest line by line, splitting on | delimiter
  2. For each entry, generates a unique symbol name: onetool_extra_main_
  3. Compiles the source file with -Dmain=onetool_extra_main_ — this renames the tool's main() function to the generated symbol via the C preprocessor
  4. Passes any extra_cflags to the compiler
  5. The resulting object file is linked into the onetool binary
  6. At startup, the extra tools are registered via the auto-generated onetool_extra_tools[] array
  7. The onetool_find_tool() function searches built-in tools first, then extra tools

This mechanism allows third-party tools to be plugged in without touching any core source files.

Global Output Redirection

OneTool supports a global -to flag that redirects stdout and stderr of any tool invocation:

onetool ping 1.1.1.1 -to /tmp/ping.log
onetool down https://example.com -to fd   # redirect to fd 3

When -to is used, the dispatcher in main() intercepts it before calling the tool:

  • If the argument is "fd", no action is taken — the caller is expected to have already set up file descriptor 3 for output capture. This is used by the TUI when running tools with output capture.
  • Otherwise, the argument is treated as a file path. The file is opened with open(path, O_WRONLY|O_CREAT|O_TRUNC, 0644), and both stdout (fd 1) and stderr (fd 2) are duplicated to the file descriptor via dup2().

Note: The -to flag must appear after the tool name, not as a global flag before it. The tool's main() never sees the -to flag — it is consumed by the dispatcher before calling the entry point.

Build System

Primary Build

make          # builds onetool
make clean    # removes built binaries

Requirements: clang and make. The build process:

  1. Compiles the shared libraries (libs/TUI/, libs/elf/, libs/memory/, libs/net/)
  2. Compiles all built-in tool sources
  3. Runs build_extra_tools.sh to compile manifest-registered tools
  4. Links everything into a single static ELF64 binary called onetool

lmake Build Tool

The bundled lmake (tools/dev/lmake.zig) is written in Zig and compiled separately. It is registered with ONETOOL_ARGV0_BINARY_PATH mode so it can locate build scripts relative to the binary path. The lmakefile in the project root is the build definition consumed by lmake — it replaces a traditional Makefile with OneTool's own build system.

InitFS

The initfs/init file is an embedded init script designed for minimal Linux environments where OneTool acts as /init (PID 1). This enables OneTool to function as the sole binary in a tiny root filesystem — a self-contained userspace.

Bootstrap Process

When OneTool is used as init:

  1. The kernel starts OneTool as PID 1
  2. If the TUI tool is launched (or taskmng/userc), the configure tool (cf) is called automatically as a fallback: if tui_init() (which needs /dev/tty) fails, it runs configure first, then retries TUI initialization
  3. Configure mounts /proc, /sys, /dev (devtmpfs), and /tmp (tmpfs) to bootstrap the basic Linux filesystem layout
  4. After this bootstrap, the full TUI becomes available

Makefile Details (lmakefile)

The project root contains lmakefile which is the build definition consumed by lmake. This is a custom build system format — not GNU Make syntax. It defines:

  • Source file lists for each tool
  • Library dependencies
  • CFLAGS, LDFLAGS
  • Output binary name and location

Error Handling Conventions

All OneTool tools follow consistent conventions:

  • Return value: 0 for success, 1 for failure
  • Errors: Printed to stderr with fprintf(stderr, ...) and strerror(errno) for system call failures
  • Usage: Invalid arguments print usage to stderr and return 1
  • Memory: All heap allocations go through ot_x*() wrappers that abort on OOM
