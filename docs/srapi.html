OneTool — SR API (Simple Rendering API) Documentation

The SR API (Simple Rendering API) is OneTool's most sophisticated and complex library, representing the culmination of the graphics subsystem development. It provides a unified abstraction layer for 2D/3D graphics rendering that spans multiple backends including CPU software rendering, GPU acceleration via Vulkan/OpenGL interoperability, and direct DRM/KMS display control. This documentation provides comprehensive coverage of every aspect of the SR API, from low-level implementation details to high-level usage patterns.

1. Overview and Architecture

1.1 Design Philosophy

The SR API was designed with several core principles that guide its architecture and implementation. First, explicit control is paramount - there are no hidden states or implicit synchronizations. Every operation must be explicitly defined by the user, making the system predictable and debuggable. Second, backend agnosticism ensures the same API works across CPU, GPU, and display backends with appropriate fallback behavior. Third, minimal abstraction overhead means thin wrappers around native APIs with zero-cost abstractions where possible. Fourth, explicit resource management follows manual creation/destruction semantics with clear ownership. Fifth, the command buffer pattern enables recording and replaying commands for efficiency.

1.2 Architecture Layers

The SR API consists of several architectural layers that work together. At the top is the public API header (srapi.h) which defines all public interfaces. Below that, the internal header (internal.h) exposes private structures and functions. The core layer implements context, buffer, image, and framebuffer management. The backend layer provides CPU and GPU implementations. The DRM layer handles direct display output. The VM layer executes shader bytecode. Each layer is carefully separated with well-defined interfaces.

1.3 Backend Support Matrix

The SR API supports three backend types. SRAPI_BACKEND_AUTO (0) automatically selects the best available backend. SRAPI_BACKEND_CPU (1) provides software rendering using optimized CPU routines. SRAPI_BACKEND_GPU (2) provides hardware acceleration via DRM/KMS when available. The CPU backend is always available, while the GPU backend requires a compatible DRM device node at /dev/dri/card0 through /dev/dri/card7 or render nodes at /dev/dri/renderD128 through /dev/dri/renderD135.

2. Public API Header Reference (srapi.h)

2.1 Opaque Types and Color

The header defines nine opaque pointer types representing core SR API objects. These are declared as forward struct declarations allowing users to work with pointers without needing to know the internal layout:

typedef struct srapi_context srapi_context_t;
typedef struct srapi_device srapi_device_t;
typedef struct srapi_buffer srapi_buffer_t;
typedef struct srapi_image srapi_image_t;
typedef struct srapi_queue srapi_queue_t;
typedef struct srapi_framebuffer srapi_framebuffer_t;
typedef struct srapi_cmd_buffer srapi_cmd_buffer_t;
typedef struct srapi_drm_display srapi_drm_display_t;
typedef struct srapi_shader srapi_shader_t;

srapi_color_t is a 32-bit unsigned integer representing ARGB color format with alpha in the most significant byte, red in bits 23-16, green in bits 15-8, and blue in bits 7-0. The macro srapi_rgba(r, g, b, a) constructs a color from four 8-bit components.

2.2 Result Type (srapi_result_t)

All SR API functions return an srapi_result_t enum value indicating success or failure. The values are: SRAPI_OK (0) for success, SRAPI_ERROR (-1) for generic failure, SRAPI_ERROR_OOM (-2) for out-of-memory conditions, SRAPI_ERROR_BAD_ARG (-3) for invalid arguments, SRAPI_ERROR_OVERFLOW (-4) for arithmetic overflow, and SRAPI_ERROR_UNSUPPORTED (-5) for unsupported features.

2.3 Backend Enumeration (srapi_backend_t)

The backend enumeration defines three values: SRAPI_BACKEND_AUTO (0) for automatic selection, SRAPI_BACKEND_CPU (1) for software rendering, and SRAPI_BACKEND_GPU (2) for hardware acceleration.

2.4 Buffer Usage Flags (srapi_buffer_usage_t)

Buffer usage is specified as a bitfield combining one or more flags: SRAPI_BUFFER_TRANSFER_SRC (1<<0) indicates the buffer will be a source for copy operations, SRAPI_BUFFER_TRANSFER_DST (1<<1) indicates it will be a destination, SRAPI_BUFFER_VERTEX (1<<2) for vertex data, SRAPI_BUFFER_INDEX (1<<3) for index data, SRAPI_BUFFER_UNIFORM (1<<4) for uniform data, and SRAPI_BUFFER_STORAGE (1<<5) for storage buffers.

2.5 Image Tiling and Usage

Image tiling can be SRAPI_IMAGE_LINEAR (1) for CPU-accessible linear layout or SRAPI_IMAGE_OPTIMAL (2) for backend-optimal layout. Image usage flags include SRAPI_IMAGE_TRANSFER_SRC, SRAPI_IMAGE_TRANSFER_DST, SRAPI_IMAGE_SAMPLED, SRAPI_IMAGE_COLOR_TARGET, and SRAPI_IMAGE_PRESENT.

2.6 Command Kinds (srapi_command_kind_t)

Command buffers support five primitive operations: SRAPI_COMMAND_CLEAR (1) fills the entire framebuffer with a solid color, SRAPI_COMMAND_FILL_RECT (2) fills a rectangle with a color, SRAPI_COMMAND_DRAW_LINE (3) draws a line using Bresenham's algorithm, SRAPI_COMMAND_FILL_TRIANGLE (4) fills a triangle using edge functions, and SRAPI_COMMAND_SHADE_RECT (5) fills a rectangle with a shader.

2.7 VM Opcodes (srapi_vm_opcode_t)

The shader virtual machine supports 15 opcodes: SRAPI_VM_END (0) terminates execution, SRAPI_VM_MOV (1) moves data between registers, arithmetic operations ADD (2) through MAX (7), load operations LOAD_INPUT (8), LOAD_UNIFORM (9), LOAD_CONST (11), output operation OUT_COLOR (10), and utility operations FRACT (12), CLAMP01 (13), MIX (14).

2.8 VM Input Registers

The VM provides six input registers: SRAPI_VM_INPUT_X (0) for pixel X coordinate, SRAPI_VM_INPUT_Y (1) for pixel Y coordinate, SRAPI_VM_INPUT_U (2) and SRAPI_VM_INPUT_V (3) for texture coordinates, SRAPI_VM_INPUT_WIDTH (4) and SRAPI_VM_INPUT_HEIGHT (5) for primitive dimensions.

3. Internal Data Structures (internal.h)

3.1 Context Structure

The srapi_context structure contains three fields: width (framebuffer width), height (framebuffer height), and backend (selected backend type). The context is the root object that manages the rendering environment.

3.2 Device Structure

The srapi_device structure contains backend (backend type), path (device path string), and fd (open file descriptor for DRM operations). For CPU backend, fd is always -1.

3.3 Buffer Structure

The srapi_buffer structure is comprehensive: device pointer, backend type, size in bytes, usage flags, data pointer (mapped memory), mapped count (for reference counting), gpu_handle (DRM handle for GPU buffers), and gpu_size (allocated size for GPU buffers).

3.4 Image Structure

The srapi_image structure contains device pointer, backend type, width, height, pitch (row stride in bytes), tiling mode, usage flags, data pointer, mapped count, gpu_handle, and gpu_size. The pitch may differ from width * 4 for alignment purposes.

3.5 Queue Structure

The srapi_queue structure contains device pointer, backend type, and family_index identifying the queue family.

3.6 Framebuffer Structure

The srapi_framebuffer structure contains width, height, pitch, pixels pointer, owns_pixels flag (whether to free pixels on destruction), and backend type.

3.7 Command Buffer Structure

The srapi_cmd_buffer structure contains items pointer (array of commands), count (current command count), and capacity (allocated capacity). Commands are stored contiguously.

3.8 DRM Buffer Structure

The internal srapi_drm_buffer structure contains fb_id (DRM framebuffer ID), handle (DRM dumb buffer handle), size, map pointer (mapped memory), and embedded framebuffer.

3.9 DRM Display Structure

The srapi_drm_display structure contains fd (device file descriptor), connector_id, crtc_id, mode (current display mode), old_crtc (saved CRTC state for restoration), has_old_crtc flag, front (front buffer index), and two buffers for double buffering.

3.10 VM Instruction Structure

The srapi_vm_inst_t structure contains op (opcode), dst (destination register), a, b, c, d (source operands), and imm (immediate value). Not all fields are used by every opcode.

3.11 Shader Structure

The srapi_shader structure contains bytecode pointer, word_count, insts (decoded instructions), inst_count, uniforms array, uniform_count, and run_count for debugging.

4. Context Management

4.1 Color Construction

srapi_rgba(uint8_t r, uint8_t g, uint8_t b, uint8_t a) constructs a 32-bit ARGB color value. The alpha component is placed in bits 24-31, red in bits 16-23, green in bits 8-15, and blue in bits 0-7. This function is inline and has zero overhead.

4.2 Backend Name Lookup

srapi_backend_name(srapi_backend_t backend) returns a human-readable string for a backend type: "auto" for AUTO, "cpu" for CPU, "gpu" for GPU, or "unknown" for invalid values.

4.3 Context Creation

srapi_create_context(const srapi_context_desc_t *desc, srapi_context_t **out) creates a new context. The desc parameter must not be NULL, and out must not be NULL. Width and height must be non-zero. If backend is AUTO, CPU is selected. The function allocates the context with calloc and initializes all fields. Returns SRAPI_ERROR_BAD_ARG if parameters are invalid, SRAPI_ERROR_OOM on allocation failure, or SRAPI_OK on success.

4.4 Context Destruction

srapi_destroy_context(srapi_context_t *ctx) destroys a context. If ctx is not NULL, it logs the destruction and frees the memory. This function is safe to call with NULL.

4.5 Backend Query

srapi_context_backend(const srapi_context_t *ctx) returns the backend type for a context, or SRAPI_BACKEND_AUTO if ctx is NULL.

4.6 Device Probing

srapi_probe_device(srapi_backend_t backend, srapi_device_info_t *out) probes for available devices. For AUTO or CPU backend, it always reports available with path "cpu". For GPU backend, it calls srapi_gpu_probe() which checks for DRM card nodes and render nodes. The info structure receives backend type, availability flag, path string, and status message.

4.7 Device Creation

srapi_create_device(const srapi_device_desc_t *desc, srapi_device_t **out) creates a device object. For GPU backend, it delegates to srapi_gpu_open_device(). For CPU backend, it probes the device and allocates the structure. The device_path from desc is used if provided, otherwise the probed path is used.

4.8 Device Destruction

srapi_destroy_device(srapi_device_t *device) destroys a device. For GPU devices, it calls srapi_gpu_close_device(). For all devices, it frees the allocated memory. Safe to call with NULL.

4.9 Submit Operation

srapi_submit(srapi_context_t *ctx, srapi_framebuffer_t *target, const srapi_cmd_buffer_t *cmd) submits a command buffer for execution. It validates all parameters, logs the submission details, and iterates through commands, dispatching to the appropriate render functions. For GPU backend with GPU framebuffer, it logs that the GPU/DRI path will write the mapped backbuffer.

5. Buffer Management System

5.1 Buffer Creation

srapi_create_buffer(srapi_device_t *device, const srapi_buffer_desc_t *desc, srapi_buffer_t **out) creates a buffer. For GPU backend, it delegates to srapi_gpu_create_buffer() which uses DRM dumb buffer allocation. For CPU backend, it allocates memory with calloc, copies initial data if provided, and sets all fields. Returns SRAPI_ERROR_BAD_ARG for invalid parameters, SRAPI_ERROR_OOM on allocation failure, or SRAPI_OK on success.

5.2 Buffer Destruction

srapi_destroy_buffer(srapi_buffer_t *buffer) destroys a buffer. For GPU buffers with mapped memory, it calls munmap. For GPU buffers with a DRM handle, it calls DRM_IOCTL_MODE_DESTROY_DUMB. For CPU buffers, it frees the data. Finally frees the buffer structure.

5.3 Buffer Queries

srapi_buffer_size() returns the buffer size or 0 if NULL. srapi_buffer_usage() returns usage flags or 0 if NULL. srapi_buffer_backend() returns the backend type or AUTO if NULL.

5.4 Buffer Read/Write

srapi_buffer_write() writes data to a buffer at a given offset. Validates the range with range_ok(), checks backend support (CPU and GPU only), copies data with memcpy. srapi_buffer_read() reads data from a buffer similarly. Both return SRAPI_ERROR_BAD_ARG for invalid parameters or unsupported backends.

5.5 Buffer Mapping

srapi_buffer_map() returns a pointer to the buffer's data. Increments the mapped reference count. Only supports CPU and GPU backends. srapi_buffer_unmap() decrements the mapped count. Both are safe with NULL.

6. Image Management System

6.1 Image Size Calculation

image_size() is a static helper that calculates pitch and total size for an image. Pitch is width * 4 bytes. Total size is pitch * height. Returns 0 on overflow or zero dimensions, 1 on success.

6.2 Image Creation

srapi_create_image() creates an image. For GPU backend, delegates to srapi_gpu_create_image(). For CPU backend, validates dimensions and tiling, allocates memory, copies initial pixels if provided. OPTIMAL tiling is not CPU-mappable.

6.3 Image Destruction

srapi_destroy_image() mirrors buffer destruction. For GPU images, calls munmap and destroys the DRM dumb buffer. For CPU images, frees the pixel data.

6.4 Image Queries

srapi_image_width(), srapi_image_height(), srapi_image_pitch(), srapi_image_tiling(), srapi_image_usage(), srapi_image_backend() all return the respective field or 0/NULL if the image is NULL.

6.5 Image Mapping

srapi_image_map() returns mapped pointer and pitch. Only LINEAR tiling is CPU-mappable. Returns SRAPI_ERROR_UNSUPPORTED for OPTIMAL tiling or if data is NULL. Increments mapped count.

7. Framebuffer System

7.1 Framebuffer Creation

srapi_create_framebuffer() creates a framebuffer from a context description. Calculates pixel count with overflow check, allocates the structure and pixel array. Sets owns_pixels=1 to indicate ownership. Backend is taken from context or defaults to CPU.

7.2 Framebuffer Destruction

srapi_destroy_framebuffer() frees pixels if owns_pixels is set, then frees the structure.

7.3 Framebuffer Queries

srapi_framebuffer_width(), srapi_framebuffer_height(), srapi_framebuffer_pitch() return dimensions or 0. srapi_framebuffer_pixels() returns the pixel array or NULL.

8. Command Buffer System

8.1 Command Buffer Creation

srapi_create_cmd_buffer() allocates a command buffer with initial capacity 0. Commands are added dynamically.

8.2 Command Buffer Destruction

srapi_destroy_cmd_buffer() frees the items array and the structure.

8.3 Command Buffer Reset

srapi_cmd_reset() sets count to 0, keeping allocated capacity.

8.4 Command Pushing

srapi_cmd_push() adds a command to the buffer. If capacity is exceeded, doubles it (starting from 16). Returns SRAPI_ERROR_OVERFLOW on size overflow, SRAPI_ERROR_OOM on allocation failure, SRAPI_OK on success.

8.5 Command Emission Helpers

srapi_cmd_emit() validates the command kind and calls srapi_cmd_push(). srapi_cmd_clear() creates a CLEAR command. srapi_cmd_fill_rect() creates a FILL_RECT command with position and dimensions. srapi_cmd_draw_line() creates a DRAW_LINE command. srapi_cmd_fill_triangle() creates a FILL_TRIANGLE command with three vertices. srapi_cmd_shade_rect() creates a SHADE_RECT command with a shader.

9. Queue Submission System

9.1 Queue Creation

srapi_create_queue() creates a queue from a descriptor. For GPU backend, delegates to srapi_gpu_create_queue(). For CPU backend, allocates and initializes the structure.

9.2 Queue Destruction

srapi_destroy_queue() frees the queue structure.

9.3 Queue Device Query

srapi_queue_device() returns the device pointer or NULL.

9.4 Queue Submission

srapi_queue_submit() validates parameters and dispatches. For CPU backend, calls srapi_submit(). For GPU backend, returns SRAPI_ERROR_UNSUPPORTED.

9.5 Copy Operations

srapi_queue_copy_buffer_to_image() and srapi_queue_copy_image_to_buffer() perform row-by-row copies between buffer and image. Validate that device matches, image is LINEAR tiling. Returns SRAPI_ERROR_UNSUPPORTED for optimal images.

10. Shader and Virtual Machine System

10.1 Shader Creation

srapi_create_shader() creates a shader from bytecode. Allocates bytecode copy, decodes instructions via vm_decode_bytecode(), allocates uniforms array. Returns SRAPI_ERROR_BAD_ARG for invalid bytecode, SRAPI_ERROR_OOM on allocation failure.

10.2 Shader Destruction

srapi_destroy_shader() frees bytecode, instructions, and uniforms arrays.

10.3 Uniform Management

srapi_shader_set_uniform() sets a single uniform by index. srapi_shader_set_uniforms() sets a range of uniforms from an array.

10.4 Bytecode Decoding

vm_decode_bytecode() parses the bytecode word stream into instructions. Each opcode has a specific format: END takes no args, MOV/LOAD_INPUT/LOAD_UNIFORM/FRACT/CLAMP01 take dst and a, LOAD_CONST takes dst and imm, arithmetic ops take dst, a, b, MIX takes dst, a, b, c, OUT_COLOR takes a, b, c, d. Returns SRAPI_ERROR_BAD_ARG on parse failure.

10.5 VM Execution

srapi_vm_run_fragment() executes a shader with 6 input values. Uses 16 general-purpose registers initialized to 0. Each instruction is decoded and executed. END terminates early. OUT_COLOR writes the final color. Returns SRAPI_ERROR_BAD_ARG for invalid parameters.

10.6 VM Operations

VM operations include: MOV (register copy), ADD/SUB/MUL/DIV arithmetic, MIN/MAX comparisons, LOAD_INPUT (load from inputs array), LOAD_UNIFORM (load from shader uniforms), LOAD_CONST (load immediate), FRACT (fractional part), CLAMP01 (clamp to [0,1]), MIX (linear interpolation), OUT_COLOR (write RGBA output).

11. DRM/KMS Display Integration

11.1 DRM Open

srapi_drm_open() opens and initializes a DRM display. Opens the device file (or auto-detects), finds a connected output, creates two dumb buffers for double buffering, sets CRTC mode, and returns the display structure.

11.2 DRM Close

srapi_drm_close() restores old CRTC state if saved, destroys both buffers, closes the fd, and frees the structure.

11.3 DRM Present

srapi_drm_present() swaps buffers via page flip. Tries DRM_MODE_PAGE_FLIP first, falls back to DRM_MODE_SETCRTC if flip fails. Waits for the flip event before returning.

11.4 Display Probing

srapi_display_probe_drm() enumerates connected displays. Opens each DRM card, queries connectors, returns information about connected outputs including preferred mode and connector type.

12. GPU Backend Implementation

12.1 GPU Probing

srapi_gpu_probe() checks for DRM card nodes (card0-card7) and render nodes (renderD128-renderD135). Returns available on first successful open.

12.2 GPU Buffer Creation

srapi_gpu_create_buffer() creates a 1D dumb buffer large enough for the requested size. Uses DRM_IOCTL_MODE_CREATE_DUMB, DRM_IOCTL_MODE_MAP_DUMB, and mmap for CPU access.

12.3 GPU Image Creation

srapi_gpu_create_image() creates a 2D dumb buffer. OPTIMAL tiling returns SRAPI_ERROR_UNSUPPORTED. Uses row-by-row copy for initial pixels.

13. CPU Software Renderer

13.1 Pixel Writing

put_pixel() writes a color to the framebuffer with bounds checking.

13.2 Clear Operation

srapi_render_clear() fills every pixel with the clear color.

13.3 Rectangle Fill

srapi_render_fill_rect() clips and fills a rectangle using a nested loop.

13.4 Line Drawing

srapi_render_draw_line() uses Bresenham's algorithm for integer line drawing.

13.5 Triangle Fill

srapi_render_fill_triangle() computes bounding box, uses edge functions for point-in-triangle testing.

13.6 Shaded Rectangle

srapi_render_shade_rect() executes the shader for each pixel, passing UV coordinates and dimensions as inputs.

14. Debug and Error Handling

14.1 Global Debug Flag

int srapi = 0 is a global flag. When non-zero, debug messages are printed to stderr with "[srapi]" prefix.

14.2 Error Storage

static char srapi_error[256] = "ok" stores the last error message. Initialized to "ok".

14.3 Error Functions

srapi_last_error() returns the current error string. srapi_set_error() formats and stores an error message using vsnprintf.

14.4 Debug Output

srapi_debugf() prints formatted debug messages when srapi flag is set.

15. PPM Image Output

15.1 Save Function

srapi_save_ppm() writes a framebuffer to a PPM file. Uses P6 (binary) format. Converts ARGB to RGB by dropping alpha. Returns SRAPI_ERROR_BAD_ARG for invalid parameters, SRAPI_ERROR on file open failure, SRAPI_OK on success.

16. Demo Tool Implementation

The demo tool (srapi_demo.c) demonstrates all SR API features. It supports CPU and GPU rendering, DRM display output, various command types, and shader execution. Key functions include low_level_smoke() testing buffers, images, queues; gpu_smoke() testing GPU path; and the main function handling CLI arguments and rendering loops.

17. Current Limitations and Future Work

  • Only supports 2D rendering operations
  • No 3D graphics pipeline (depth/stencil buffers, 3D shaders)
  • No descriptor set/resource binding system
  • DRM backend requires direct hardware access (no Wayland/X11)
  • No validation layers or extensive error checking
  • Single-threaded design
  • No async command submission
  • Shader VM is interpreted, not JIT-compiled
