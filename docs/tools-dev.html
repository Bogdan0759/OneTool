mlink — Minimal ELF64 x86-64 Linker

Entry: ml() in tools/dev/mlink/

A minimal but fully functional linker for ELF64 x86-64 relocatable object files (.o). It takes one or more object files (and optionally simple .a archives) and produces a static ELF64 executable. mlink is the most complex tool in OneTool, spanning 10 source files with ~1500 lines of code.

Section Classification — classify_section()

Each ELF section is classified into one of 5 kinds based on its type, flags, and name:

ML_SEC_SKIPNo SHF_ALLOC flag, or .eh_frame, .comment, .note.GNU-stack sections
ML_SEC_TEXTSHF_EXECINSTR flag set (executable code)
ML_SEC_RODATAAllocatable, not writable, not executable (read-only data)
ML_SEC_DATASHF_WRITE set and SHT_PROGBITS (writable initialized data)
ML_SEC_BSSSHF_WRITE set and SHT_NOBITS (zero-initialized data)

Archive Parsing — load_archive()

mlink supports three archive formats:

  • POSIX/BSD style (#1/ prefix): The member name is stored at the beginning of the member data, followed by the actual object content
  • GNU style (/123 long names): The archive has a // member containing a string table; member names reference offsets into it
  • Standard short names (16-byte header field): Names are stored directly in the archive header, space-padded, with optional trailing '/'

The parser also skips symbol table members (/ and /SYM64/). Archive member alignment is enforced (odd sizes are padded).

Linking Pipeline — 6 Phases

Phase 1: Load Inputs (ml_load_input())

Each input path is read from disk via ml_read_file(). The file is identified as either:

  • Archive (.a): Checked via ARMAG magic ("!\n"). Parsed by load_archive(), each ELF object within is parsed and added to the context as an unselected archive member.
  • ELF object (.o): Checked via ELFMAG magic. Parsed by ml_parse_elf_object() and added as a selected (non-archive) object.

Phase 2: Parse ELF Objects (ml_parse_elf_object())

Uses the shared ot_elf_parse() from libs/elf to validate the ELF header, then:

  1. Section loading: Copies section names, types, flags, sizes, aligns. Classifies each section via classify_section(). Copies section data for PROGBITS sections.
  2. Symbol loading: Locates SHT_SYMTAB (entry size must be 24). For each symbol: reads name, bind (STB_GLOBAL/STB_LOCAL/STB_WEAK), type, shndx, value, size, and determines if undefined or common.
  3. Relocation loading: Locates SHT_RELA (entry size 24) and SHT_REL (entry size 16). For each relocation: reads offset, symbol index, type, and addend (if RELA).

Phase 3: Symbol Resolution (ml_resolve_symbols())

Three sub-steps:

3a. Archive Member Selection (select_archive_members())

Iterates archive members in a fixed-point loop. For each unselected archive member, if any of its defined global symbols are referenced by already-selected objects, the member becomes selected. This loop repeats until no more members are selected (standard Unix linker semantics).

3b. Global Symbol Definition (define_global())

For each selected object's global symbols:

  • Common symbols: If not already defined, the largest size wins (standard COMDAT-like behavior)
  • Defined symbols: If already defined, strong overrides weak; duplicate strong symbols produce an error; duplicate weak symbols are ignored
3c. Undefined Reference Tracking (record_undefined())

Records all undefined references. After resolution, any symbol that is strongly referenced but neither defined nor common produces an "undefined symbol" error.

Phase 4: Layout (ml_layout())

Computes output addresses and file offsets for all sections:

4a. Segment Detection

Scans all sections to determine which segments are needed:

  • RX segment — required if any TEXT sections exist
  • RO segment — required if any RODATA sections exist
  • RW segment — required if any DATA, BSS, or COMMON symbols exist
4b. Section Ordering

Sections are assigned in this order within each object:

  1. .text sections — aligned, placed in RX segment
  2. .rodata sections — aligned, page-aligned boundary from RX end
  3. .data sections — aligned, page-aligned boundary from RO end
  4. .bss sections — placed after .data (not written to file)
4c. Segment Boundaries
SegmentFile OffsetVirtual AddressFile SizeMemory Size
RX (text)0base_addrtext_sections_endsame
RO (rodata)page_align(rx_end)base + offsetrodata_end - offsetsame
RW (data+bss)page_align(ro_end)base + offsetdata_end - offsetbss_end - offset
4d. Common Symbol Allocation

Common symbols are placed after all data sections, with their requested alignment. The largest alignment wins. The BSS memory size is extended to cover common symbols.

4e. Global Value Resolution

Each global symbol's value is computed:

  • Defined symbols: section.out_addr + symbol.value
  • Absolute symbols: symbol.value (SHN_ABS)
  • Common symbols: base_addr + common_cursor (with alignment)

Entry symbol is looked up; if not found, linkage fails.

Phase 5: Apply Relocations (ml_apply_relocations())

For each selected object, each relocation is patched into the section image:

TypeWidthComputationDescription
R_X86_64_NONE0—No operation
R_X86_64_648S + A64-bit absolute address
R_X86_64_PC324S + A - P32-bit PC-relative
R_X86_64_PLT324S + A - P32-bit PLT-relative (treats as PC32 for static link)

R_X86_64_32S4S + A (signed)32-bit absolute (sign-extended)
R_X86_64_PC648S + A - P64-bit PC-relative

Where: S = symbol value, A = addend, P = relocation position (section address + offset), Z = symbol size.

Addend Handling
  • RELA relocations (SHT_RELA): The addend is stored explicitly in the relocation entry
  • REL relocations (SHT_REL): The addend is read from the section data at the relocation offset (read_implicit_addend())
Overflow Checking

Every relocation that writes a value has overflow checks via checked_u32(), checked_i32(), checked_u16(), checked_i16(), checked_u8(), checked_i8(). On overflow, an error is reported with the relocation type and section name.

Phase 6: Emit Output (ml_emit_output())

Generates the final executable:

6a. ELF Header

A 64-byte ELF64 header is constructed:

  • Magic: 0x7f ELF
  • Class: ELFCLASS64 (2)
  • Data: ELFDATA2LSB (1, little-endian)
  • Version: EV_CURRENT (1)
  • OS/ABI: ELFOSABI_SYSV (0)
  • Type: ET_EXEC (2)
  • Machine: EM_X86_64 (62)
  • Entry: resolved entry address
  • Program header offset: right after ELF header (64 bytes)
  • Program header size: 56 bytes, count = phnum
  • Section header table: not written (SHN_UNDEF)
6b. Program Headers

1 to 3 PT_LOAD segments are created:

SegmentFlagsAlignment
RX (text)PF_R | PF_X0x1000 (page)
RO (rodata, optional)PF_R0x1000
RW (data+bss, optional)PF_R | PF_W0x1000

Each PT_LOAD has: p_offset, p_vaddr, p_paddr (= vaddr), p_filesz, p_memsz, p_align.

6c. Section Data

All selected objects' sections are copied to the output buffer at their assigned offsets. BSS sections are not copied (they are zero-initialized by the OS loader).

6d. File Writing

Written with ml_write_file_mode() with mode 0755 (executable). On --dry-run, no file is written.

6e. Link Map Output

The ml_print_map() function outputs:

  • Output file path and dry-run indicator
  • Base address and entry symbol with address
  • Each segment: type, offset, vaddr, filesz, memsz
  • Each included section: address, size, kind, name, object file
6f. Symbol Table Output

The ml_print_symbols() function outputs all defined global symbols with their resolved addresses.

Usage

onetool mlink [options] file.o [lib.a ...]

Options:
  -o file            Output executable (default a.out)
  -e symbol          Entry symbol (default _start)
  --base addr        Image base address (default 0x400000, must be page-aligned)
  -Map file          Write link map to file
  --print-map        Print link map to stdout
  --print-symbols    Print global symbols to stdout
  --dry-run          Parse, resolve and layout without writing output
  -v, --verbose      Print archive member selection details
  -h, --help         Show help

Example

onetool mlink -e _start -o myapp start.o main.o libfoo.a

Limitations

  • Only ELF64 little-endian x86-64 relocatable objects
  • No dynamic linking (static executables only)
  • No shared library support
  • No section header table in output (SHN_UNDEF)
  • No debug section preservation
  • Simple archive format only (no thin archives, no dash archives)
  • Single architecture (no fat binaries)

lmake — Bundled Build Tool

Source: tools/dev/lmake.zig (807 lines)

Language: Zig

Entry: lk() — exported as pub export fn lk(argc: c_int, argv: [*][*:0]u8) c_int

argv0_mode: ONETOOL_ARGV0_BINARY_PATH — argv[0] is set to the binary path so lmake can locate its build scripts relative to the executable

lmake is a custom build system written in Zig that reads lmakefile — the project's build definition file. It replaces a traditional Makefile with OneTool's own DSL. Without lmake, the project cannot be built. It is compiled as part of OneTool and invoked via onetool lmake [target].

Architecture — Three-Phase Pipeline

lmake is structured as a classic compiler pipeline with Tokenizer → Parser → Executor phases, all in a single file:

Executor~150Runtime: evaluates variables, executes task commands via shell

lk()~40C ABI export: allocates arena, parses args, calls runLmake()

Identifiers are validated with isIdentStart() (alphabetic or underscore) and isIdentContinue() (alphanumeric or underscore). Comments (//) are skipped entirely during tokenization. The tokenizer tracks line and column numbers for error reporting.

Parser — Parser struct

The parser consumes tokens and constructs a program model with two main data structures:

Program Model

const Program = struct {
    vars: std.StringArrayHashMap([]const u8),       // Variable name → value
    task_order: std.ArrayListUnmanaged([]const u8), // Task names in definition order
    tasks: std.StringArrayHashMap(Task),             // Task name → Task struct
};

const Task = struct {
    name: []const u8,         // Task name (e.g. "all", "clean")
    body: []const u8,         // Raw command text to execute
    deps: [][]const u8,       // Dependency task names
};

Parsing rules:

  • Variable declaration: string NAME = "value"; — stores in program.vars. Variables can reference other variables using @(NAME) syntax in string values.
  • Task definition: task "name" [deps...] { body } — stores the task name, dependency list, and body text.
  • Variable references: Inside string values, @(VARNAME) is replaced with the variable's value during variable loading (before execution). References are resolved with dependency order: the parser collects all @(...) references and substitutes them by looking up in program.vars.

Executor — Executor struct

The executor runs tasks by invoking system commands via shell:

loadVars()

Iterates all declared variables in definition order. For each variable, scans the value for @(NAME) references and substitutes them. This enables variables to reference previously defined variables (e.g., MAIN_OBJ = "main.o" and later OBJS = "@(MAIN_OBJ) tools.o").

execTask(name)

  1. Looks up the task by name in program.tasks
  2. If not found: tries "all" or the first task in definition order
  3. Recursively executes all dependency tasks first (via execTask())
  4. If the task has a body, substitutes variable references in the body text using @(NAME) syntax
  5. Executes the substituted command via std.Io.Command.run() which spawns a shell (/bin/sh -c "...")
  6. Checks the exit code — if non-zero, returns error.CommandFailed

format() — Custom Formatter

A printf-style string formatter supporting:

  • %s — string
  • %d, %i — signed integer
  • %u — unsigned integer
  • %x, %X — hexadecimal (lower/upper)
  • %b — binary
  • %c — character from integer value
  • %% — literal percent
  • Padding: %10s (right-align), %-10s (left-align), %010d (zero-padded)

All numeric formatting uses std.fmt.parseInt() for parsing and std.fmt.bufPrint() for output. Arguments are passed as []const u8 slices and parsed to integers on demand.

CLI Entry — runLmake()

Parses command-line arguments:

lmake [-f ] [target]
lmake --list          # list available targets
lmake -h, --help      # show usage
  • Default file: lmakefile in the current directory
  • Default target: "all" if defined, otherwise the first task in the file
  • --list: Prints all task names in definition order

Reads the lmakefile (max 10MB via .limited(10 * 1024 * 1024)), parses it, loads variables, finds the entry target, then executes it with full dependency resolution.

C ABI Export — lk()

The lk() function is exported with pub export fn so it can be called by OneTool's C dispatcher with standard C ABI (argc/argv):

  • Creates a std.Io instance with threaded I/O and inherits the process environment from std.c.environ
  • Uses a DebugAllocator for the main heap and an ArenaAllocator for the parser/executor (all memory freed at once via arena.deinit())
  • Converts C argv pointers to Zig slices
  • Calls runLmake() — on error, prints the error name and returns 1
  • Returns 0 on success
